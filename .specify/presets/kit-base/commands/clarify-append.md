## Kit rules: after the command

These steps belong to this command. Do them in order, before you report completion.

Goal: a round that ends with no `open` row means the plan can start, because nothing the plan refuses on is left: no `[NEEDS CLARIFICATION]` anywhere in `spec.md` (the table included) and no unmarked checklist item.

1. Bring the `## Open Questions` table of `spec.md` up to date, and delete the template's example row if it is still there. Add a row for each pending item: a question left without an answer, each `[NEEDS CLARIFICATION]` (copy its question into the row without the marker text) and each "Deferred" item. Give every row one state:
   - `open`, the default;
   - `to plan`, only for a how question (technology or implementation) and only with the user's OK;
   - `resolved`, with the answer, once the spec says it or once the user waives a checklist item.

   A `resolved` or `to plan` row leaves no `[NEEDS CLARIFICATION]` marker in the spec body: the answer replaces the marker of a `resolved` row, and a pointer such as "see Open Questions: <short question>, to plan" replaces the marker of a `to plan` row.

   Every default you choose without asking the user, in the command above or in this section, is a row too: a value that changes the product, such as a number, a limit, a range, an order or a message the user sees (for example "5 failed attempts, a 15-minute lock" when the user only chose a temporary lock). Write it as a `resolved` row with an Answer that starts with "Padrão do agente:" and gives the value, and put the same value in the spec body. Such a row marks a checklist item only when it answers that item's text; when it does, name the item in the row's question. A how (technology or implementation) is never a default: it follows step 6.
2. Go through the checklists. First mark `[x]` each unmarked item (`- [ ]`) in `FEATURE_DIR/checklists/*.md` that the spec now answers, each one whose row is `resolved`, and each one whose question is now a `to plan` row: the user agreed to defer it, and the plan answers it in `research.md`. Then give each item that is still unmarked and has no row a new `open` row that names the item, so that every unmarked item has an `open` row. Last, only if no row is `open`, run each checklist that fits the feature and is not in that folder yet:
   - `/speckit-checklist security` when the feature touches login, data, an API, a secret, payment, file upload, an external call or a webhook, or personal data;
   - `/speckit-checklist ux` when the feature has a screen.

   A round whose argument names a change to the spec, from a brainstorming re-entry (it starts "Change already approved in the brainstorming") or a prototype finding (it starts "Prototype finding that changes the what of the feature"), runs the checklists even with an `open` row, judging the list above again with that change: it runs each one that now fits and is not in that folder yet, and runs again each one already there whose subject the change touches (delete the old file and the `open` rows that name its items first, then run the command, so the new items are judged). Pass the depth `Standard`, the audience `Reviewer (PR)` and the focus in the argument, so that it asks nothing: `/speckit-checklist security depth Standard, audience Reviewer (PR), focus login and sessions`. Judge each new item the same way. Mark `[x]` only the items the spec answers, the items whose row is `resolved` and the items whose question is a `to plan` row; each other item stays unmarked and becomes a new `open` row. Never mark any other item: an unmarked item makes the Executor's `/speckit-implement` stop and ask. Match a row written before the old file was deleted to a new item by the item's text, never by its ID: the new file starts again at CHK001.
3. Confirm the agent's defaults before the round closes. When this round wrote a "Padrão do agente:" row, give the context in the chat (each default, its value and what it changes), then ask one AskUserQuestion (header "Padrões") that lists them, with the options "Confirmar todos" and "Ajustar" (which ones and the new values go in "Other"). A confirmed row stays as it is. A value the user changes becomes the user's answer: replace the Answer cell, without "Padrão do agente:", and the value in the spec body; the row stays `resolved`, so the items step 2 marked keep their `[x]`. A default the user wants to leave undecided becomes an `open` row, and its value leaves the spec body: uncheck (`- [ ]`) each checklist item that step 2 marked because of this default (the items its question names), so that every unmarked item keeps its `open` row and every `open` row was asked this round. An answer that changes the approach or the scope goes to the first case of step 6.
4. Update `phases.clarify` in `FEATURE_DIR/progress.yml`, creating the file if it is missing and leaving the other phases as they are. Set `status` to `in_progress` while a row is `open` and to `done` when none is, `date` to today (`YYYY-MM-DD`), `rounds` to the previous value plus one (1 on the first round), and `open` and `to_plan` to the number of rows in each state, counted in the table:

```yaml
phases:
  clarify: {status: in_progress, date: 2026-10-03, rounds: 2, open: 1, to_plan: 1}
```

   When this round changed `spec.md` and `phases.plan` exists, also delete `phases.plan`, `phases.tasks` and a `phases.prototype` that is `skipped`: they describe the old spec, and `/speckit-plan` and `/speckit-tasks` write them again (the brainstorming re-entry does the same).

5. Call `/speckit-git-commit` as the `after_clarify` hook. The hooks above ran before this section and did not see `progress.yml`, so this call is the one that commits it.
6. Decide the next move yourself, without asking permission to go on. Take the first case that fits:
   - an answer changed the approach or the scope: go back to the `brainstorming` skill, which reviews the approach and edits this `spec.md`. Never run `/speckit-specify` again for this feature;
   - a row is still `open`: a row never stays `open` for two rounds without the user having been asked about it, so ask the user directly about each `open` row that this round did not ask. A how question (technology or implementation) always ends as `to plan`: ask whether the user wants to decide it now or leave it to the plan, and write the decision, if there is one, in the row's Answer cell (the plan carries it into `research.md` as the Decision). The how never enters the spec body. For any other question, including a constraint the user imposes (a what, not a how), ask for the answer, put it in the spec and mark the row `resolved`; a checklist item the user waives has nothing to put in the spec, so note the waiver in the Answer cell. Clean `spec.md` as step 1 says, then run `/speckit-clarify` again with the rows that are still `open` as its argument (the command sets its priorities from that argument), so that the next round records the answers;
   - no row is `open`: ask the user "Criar o plano ou fazer um protótipo antes?", then run `/speckit-plan` or `/prototipo`, as they choose.
