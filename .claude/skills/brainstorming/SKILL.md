# Brainstorming: kit layer

Read `upstream/SKILL.md`, in this skill's folder, with the Read tool and follow it, with the differences below. Where they disagree, the differences win.

This skill serves the main session, which plans. The Executor and the Revisor, the subagents that `/implementar` calls, do not brainstorm: the spec, the plan and their request are their approved design.

## Differences

1. **A project: the design goes to the Spec Kit.** The upstream's conversation stays: "Look Before You Ask", "Your First Message", "The Conversation" with its approaches, and "Play It Back". When "Size the Work" says a project, its design doc, the approval of that doc and `writing-plans` become one step: when the user approves the design you played back, run `/speckit-specify` with the whole agreed design as its description, covering what "The Written Design" lists (intent and the why, goals, non-goals and anti-goals, constraints, the approaches and the one picked, what the user decided, and what is left to the builder). When you ask for that approval, say that it runs `/speckit-specify`, which creates the branch `spec/NNN-name` and the folder `specs/NNN-name/`. Write no design doc in `docs/superpowers/specs/`, commit nothing yourself and skip the builder check: the written spec is reviewed in the `/speckit-clarify` rounds that `/speckit-specify` starts. So, for a project, the HARD-GATE reads: the design approval permits `/speckit-specify`, the only skill you invoke at the end, never `writing-plans`.
2. **A small change: product code goes through `/implementar`.** This session does not write product code or tests: the Executor writes them, through `/implementar`. When a small change touches them, its short design doc is the four-part text, shown in the chat and not saved: the title line, `feat: <topic>` or `fix: <topic>`, then the objective, why, constraints and done (the test that proves it). With the user's approval of that text, run `/implementar` with it as its argument: for a small change, the HARD-GATE reads: the approval of the four-part text permits `/implementar`, never `writing-plans`. The same holds for the quick, clear task of "First: What Do You Actually Know?", which you would otherwise just do. When the user opts out of the questions, say in one line whether it is a small change or a project: a small change that touches product code or tests goes as this four-part text to `/implementar`; a project goes to `/speckit-specify` with what the user said as its description (item 1).
3. **Spike: code only through `/prototipo`.** A spike ("Spike to feel things out") that needs code writes it only through `/prototipo`, in the folder of the feature it serves (`specs/NNN-name/prototipo/`); its first step is the spike's approval. While that feature has no folder in `specs/`, answer without writing code. Mockups and throwaway screens in the visual companion are not product code: they stay in `.superpowers/`.
4. **Back from the clarify.** `/speckit-clarify` sends you here when an answer changes the approach or the scope of a feature that already has a spec. Treat the same way a change the user asks for in a feature that already has a spec. When the feature's `progress.yml` has `spec_pr` and `gh pr view <spec_pr> --json state --jq .state` prints `MERGED`, the spec is frozen: read the section "The spec during implementation" of `.claude/skills/implementar/SKILL.md` with the Read tool, do what it says, and stop here. When `gh` cannot tell (not installed, or no login), say so and stop. Otherwise, lay out the approaches and play back the part that changes, as a project does; while the spec PR is still open, the end of `/speckit-tasks` sends the new commits to it. Once the user approves it, do these in order:
   1. Be on the feature's branch (`git checkout spec/NNN-name`) and make `.specify/feature.json` name its folder (`{"feature_directory": "specs/NNN-name"}`, the pointer `/speckit-clarify` reads); otherwise the round and its commit hit the current feature and branch.
   2. Edit that feature's `specs/NNN-name/spec.md` directly: the sections the change touches, Out of Scope included, and its Open Questions table (a row the change answers becomes `resolved`; a new doubt becomes an `open` row).
   3. In `specs/NNN-name/progress.yml`, set `phases.brainstorm` to `status: done` with today's date, and `phases.clarify` to `status: in_progress`, keeping its `rounds` and counting `open` and `to_plan` again from the table. Delete `phases.plan`, `phases.tasks` and a `phases.prototype` that is `skipped`: they describe the old spec, `/speckit-plan` and `/speckit-tasks` write them again, and `/andamento` shows a missing phase as not started. A `prototype` that is `done` stays; the user decides whether to run `/prototipo` again. Leave the rest as it is.
   4. Run `/speckit-clarify` again, without asking, with an argument that starts "Change already approved in the brainstorming, not an answer of this round; do not send it back there:" followed by what changed. The round reviews the spec against it and commits these edits.

   Never run `/speckit-specify` again for this feature: it would create another folder and another branch.
5. **Visual companion.** Start it with the project root as `--project-dir`: `bash .claude/skills/brainstorming/upstream/scripts/start-server.sh --project-dir <project root> --open`. The screens and the state go to `.superpowers/`, which git already ignores and this session's hook lets you write.
6. **Questions through AskUserQuestion.** Every question to the user, in every step above and the upstream's, the visual companion's offer included, goes through the AskUserQuestion tool, never as plain text in the chat. Give each question's context in the chat before the call: what it decides, what each option changes and your recommendation. The upstream's one question per message stays. For one of its open questions, say in the chat that the options are only examples, and keep them few and short: the user's own words go in "Other". Give no recommendation and no per-option consequences for it: say only what the answer decides.
7. **Paths and missing skills.** The upstream's paths start from `upstream/`: the `visual-companion.md` "in this directory" is `upstream/visual-companion.md`, and the `scripts/` that guide runs are in `upstream/scripts/`. `superpowers:writing-plans` is not in this project: item 1 replaces it for a project, item 2 for a small change.
